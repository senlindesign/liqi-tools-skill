# 使用时 Onboarding

目标是让用户自然进入一次有出处的检索，不要求用户理解数据库字段。

## 路由

| 用户表达 | 入口 | 首要结果 |
|---|---|---|
| “用什么”“推荐几个” | Task | 最多 3 个工具与具体使用场景 |
| “怎么完成”“完整流程”“谁做过” | Workflow / Case | 创作者、阶段、工具与边界 |
| “大家怎么用 Notion” | Tool | 不同创作者各自的用法与来源 |

具体请求直接检索。模糊请求只问一个会改变排序的问题，例如平台或是否接受付费；不要让用户填写表单，也不要每次都复述 Skill 介绍。

## 约束

检索可识别平台，以及免费/开源、团队协作、离线/本地等明确词语。把这些词当成约束，不要当成任务主题。若历史访谈没有足够信息，应说明证据不足，而不是推断兼容性、价格或隐私表现。

## 结果状态

- `已核对访谈`：创作者、场景、证据和来源已人工核对。
- `访谈线索`：由访谈上下文机器提取，需要谨慎表达；重要结论应打开原访谈核对。

即使工具实体整体仍是 provisional，只要当前任务命中了已核对的创作者用法，首要状态应显示 `已核对访谈`。

## 无结果

没有足够证据时：

1. 明确说明利器语料中没有找到可靠结果。
2. 使用返回的建议词换一种说法再查一次，或减少限制。
3. 任务可能是完整流程时切换 Workflow；点名工具时切换 Tool。
4. 仍无结果就停止，不用常识填补成“利器创作者推荐”。

## 第一轮验收

- 最多 3 个候选。
- 每项都有场景、创作者、短证据转述和原始链接。
- Workflow 先讲人和任务；Tool 保留不同人的差异。
- 只有能帮助下一轮排序时才追问。
- 不把历史访谈当成当前产品事实。
